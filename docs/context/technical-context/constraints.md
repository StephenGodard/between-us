## Open technical constraints

- **Known:** The owner ranks backend skills as .NET, Python, TypeScript/Node, Java, PHP, strongest to weakest. ADR 0001 selects ASP.NET Core/SignalR for the demo; exact framework version is `Not provided.`
- **Known:** Two distinct devices on the same LAN are required. The current `BroadcastChannel` implementation only connects compatible browsing contexts on the same origin ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)); it cannot satisfy the new scope.
- **Not provided:** The secure-origin mechanism for both LAN devices and actual WebRTC connectivity on the chosen network. These need an end-to-end check; being on one LAN does not guarantee a call.
- **Not provided:** Exact PC and phone browsers, internet conditions, offline use, accessibility criteria, budget, deployment provider, expected load and availability. Do not invent targets.
- **Known:** The selected demo entry is open subject → wait → list and join (A-30 to A-33). The opener can cancel while waiting (A-35); joiner exit returns the same subject to waiting after clearing messages (A-36). **Not provided:** Session identifier, concurrent-join handling, reconnect rule, and how long in-memory state may remain after an unexpected disconnect. Record these in the scoped PRD and design before implementation.
- **Known:** The owner's PC is the LAN host for local testing (A-35), and ADR 0001 selects one trusted HTTPS browser origin routing to both services. **Not provided:** Address, ports, certificate setup and firewall access. A process bound only to `127.0.0.1` is reachable only from its own machine.
- A cross-device microphone call requires a secure browser context and permission ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)). Network traversal and any relay service are undecided; a local two-tab call does not validate remote connectivity.
